# Build & release the mobile apps (customer-app, driver-app)

`customer-app` and `driver-app` are Expo (React Native) apps. They **do not
deploy to a URL** — they build to the App Store and Google Play using **EAS
Build**. That needs accounts that are yours:

- An **Expo (EAS)** account — free to start: <https://expo.dev>
- An **Apple Developer** account (US$99/yr) for iOS / TestFlight
- A **Google Play Developer** account (US$25 once) for Android

> These accounts and their credentials are yours and cannot be provisioned by
> anyone else. The steps below are what you run once the accounts exist.

**Read `app-store-release-readiness.md` first.** This page is the mechanics;
that page is what has to be true before running any of it. Several items there
are automatic store rejections and none of them are fixed by a build command.

## What is already committed

Both apps now carry an `eas.json` with three profiles, so `eas build:configure`
is **not** needed — running it would overwrite them.

| Profile | Distribution | Android artefact | For |
| --- | --- | --- | --- |
| `development` | internal | APK | Dev client against a local backend |
| `preview` | internal | APK | Device testing against the live API — sideload / TestFlight |
| `production` | store | AAB | Store submission |

Each profile sets `API_BASE_URL` in `env`. `app.config.js` reads it and injects
it into `expo.extra.apiBaseUrl`; the `production` and `preview` profiles point
at the deployed Cloud Run API, `development` at `localhost:3000`.

## Versioning

`cli.appVersionSource` is **`remote`**: EAS holds the build number and
`autoIncrement: true` on the `production` profile raises it on every production
build, so nobody has to remember to bump it and two uploads can never collide.

`app.json` carries `version: "1.0.0"` plus `ios.buildNumber: "1"` and
`android.versionCode: 1`. Those are the **seed** values EAS initialises the
remote counter from on the first production build; after that the remote value
wins and the committed ones are ignored. Change `version` by hand for a real
release (1.0.1, 1.1.0); never hand-edit the build number.

## Credentials: EAS secrets, never the repo

The Maps key is the only build-time credential either app needs, and it is
**not** in `eas.json` — `eas.json` is committed.

```bash
cd customer-app     # then repeat for driver-app
eas secret:create --scope project --name GOOGLE_MAPS_API_KEY --value '<key>'
```

`app.config.js` reads `GOOGLE_MAPS_API_KEY` from the build environment and
injects it into the Android, iOS and `extra` slots. The committed `app.json`
keeps an **empty** placeholder, and a missing key is deliberately not fatal:
the map panels degrade to the "map unavailable" card. See
`google-maps-keys.md` — and note the customer app's key is in that repo's git
history and must be rotated before it is used again.

## Icons and launch assets

`assets/README.md` in each app is the source of truth. In short: `icon.png` is
a **1024 × 1024 PNG with no alpha** (App Store Connect rejects a JPEG and
rejects alpha outright — the apps used to point at a 1600 × 384 JPEG, so no
binary could have been uploaded), `adaptive-icon.png` is a transparent PNG
drawn inside the Android safe zone, and both are regenerated by
`scripts/generate-icons.py`.

The current `icon.png` is a **stopgap**: technically valid, visually a wordmark
letterboxed in a square. Replacing it needs a square brand mark from the
restaurant, not a code change.

## Build

```bash
npm i -g eas-cli
cd customer-app
eas login

# Internal test build first — this is the one that goes on a real handset
eas build --platform all --profile preview

# Store-ready binaries
eas build --platform android --profile production
eas build --platform ios --profile production
```

## Distribute

- **iOS:** `eas submit -p ios` → TestFlight → App Store review.
- **Android:** `eas submit -p android` → Play internal testing → production.
- **Over-the-air JS updates** (no store review, for JS-only changes):
  `eas update --branch production`.

`submit.production` in `eas.json` is intentionally empty. Filling it needs
`appleId` / `ascAppId` / `appleTeamId` and a Play service-account key — none of
which exist yet, and none of which belong in the repo. `eas submit` prompts for
them and stores them against the EAS project.

**The driver app should almost certainly not go to the public App Store** — it
has no public sign-up, which Apple rejects under Guideline 4.2. See
`app-store-release-readiness.md` § B11.

## Order of operations

1. Backend live (`deploy-backend-gcp.md`) → you have the API URL.
2. Maps mobile keys created and the old one rotated (`google-maps-keys.md`).
3. `eas secret:create` for `GOOGLE_MAPS_API_KEY` in both apps.
4. `eas build --profile preview` → install on a real iPhone and a real Android,
   walk a whole order through.
5. `eas build --profile production` → `eas submit`.
